nudge: Google Calendar reminders -> Discord / Telegram

This simple app sends reminders based on GCal events.

The basic idea is that there is a service running on the Raspberry Pi, which uses GCal reminder settings to trigger notifications to Discord or Telegram. (NB: This is a point of discussion in figuring out the requirements).

The notification trigger times would be determined by the GCal even settings. So for example, if the event has a notification setting of one hour before the event, that's when the notification would trigger. Events can have multiple notification triggers.

The messages would need to be nicely formatted and might include emoji and other text-based touches.

1. FEASIBILITY SUMMARY
----------------------
Feasible, and small. The Google Calendar API gives us each event's reminder
settings, a Raspberry Pi can easily run a small polling service, and both
Discord and Telegram accept formatted messages over a plain HTTPS POST.
Estimated effort: a few evenings for a solid MVP.

Key facts and gotchas that shape the design:

a) Reading reminder settings. events.list returns `reminders` on each event:
   - `useDefault: true`  -> the calendar's default reminders apply. These are
     NOT on the event; fetch them from calendarList.get(calendarId)
     .defaultReminders.
   - `overrides: [{method: "popup"|"email", minutes: N}, ...]` -> the
     event's own reminders (max 5 per event, max 40320 min = 4 weeks).
   - For ALL-DAY events, `minutes` counts back from midnight at the start of
     the event date, in the calendar's time zone. For example, "day before at
     5pm" is stored as 420.

b) Reminders belong to each user. Every user has their own reminder settings
   for a shared event. So we must read the calendar AS YOU (OAuth user
   credentials). A service account with the calendar shared to it would see
   its own reminders (none), not yours. That rules out the usual
   "service account on a server" shortcut.

c) Refresh tokens expire after 7 days in "Testing" mode. This matters most on
   a headless Pi. If the Google Cloud OAuth consent screen is left in
   "Testing" status, refresh tokens expire after 7 days and the service
   silently dies once a week. Fix: set the app to "In production". An
   unverified personal app is fine; you'll click through an "unverified app"
   warning once. Use only the read-only scope
   (calendar.readonly, or calendar.events.readonly + calendarlist.readonly).

d) Headless auth. Run the one-time OAuth consent flow on your laptop, then
   copy the resulting token file to the Pi. Alternatively, run it on the Pi
   through an SSH port-forward to the loopback redirect.

e) Polling, not push. The Calendar push API (events.watch) needs a public
   HTTPS webhook, which is overkill for a Pi on a home network. Polling every
   few minutes stays far inside the free quota (1M requests/day).

f) Recurring events. Use `singleEvents=true` so each recurrence comes back as
   its own instance with its own start time and reminders.

g) Clock accuracy. The Pi has no RTC, so make sure NTP sync
   (systemd-timesyncd) is on. Otherwise notifications fire at the wrong time
   after a reboot.

2. DISCORD vs TELEGRAM (the open question)
------------------------------------------
Discord (webhook)
  + Easiest possible setup: create a webhook in a channel, POST JSON to it.
    No bot, no tokens beyond the URL.
  + Rich "embeds": colored side bar, title, fields, timestamps, which suit
    nicely formatted reminders.
  - Phone push notifications depend on your Discord notification settings for
    that server/channel. Discord can feel noisy or easy to miss.
  - One-way only. No interactive buttons without a full bot.

Telegram (bot)
  + Very reliable, prompt phone push notifications. Feels like a text
    message.
  + A path to interactivity later (inline buttons like "Snooze 10 min" or
    "Done"). That needs the bot to also poll for updates.
  - Slightly more setup: create a bot with @BotFather, message it once, look
    up your chat_id.
  - MarkdownV2 escaping is fiddly. Use `parse_mode=HTML` instead.

DECISION (2026-09-21): Discord first, since it's already set up.
UPDATE (2026-09-22): Telegram added. Both run in parallel during a trial
week; turning one off is one config section.

Original recommendation: build a small Notifier interface and ship BOTH early.
Each is about 30 lines. If you want to pick one for the MVP, use Telegram if
phone push reliability matters most, or Discord if you already live in
Discord and want the richer visual formatting.

3. REQUIREMENTS DECISIONS (resolved 2026-09-21)
-----------------------------------------------
[x] Calendars: a configured list of calendar IDs (not primary-only).
[x] Reminder method: popup only. Email reminders are ignored. Events that
    should notify get popup reminders set in GCal.
[x] Duplicate GCal notifications: acceptable. The user will disable
    Google's notifications or live with them. No action for the app.
[x] Declined events: skip them. This will rarely come up, because the target
    use is a personal calendar, not a meeting-heavy work calendar.
[x] Missed reminders: send if within a 15-minute grace window and mark them
    "late"; otherwise skip and log. The Pi is expected to be always on.
[x] Message content: event title only, to start. No description, location,
    or links. Keep it very simple.
[x] Quiet hours: not needed.
[x] Discord vs Telegram: Discord (webhook) first, since the user already
    uses it. Telegram comes later, behind the same Notifier interface.
[x] Access method: Google Calendar API with OAuth. Tested and rejected the
    secret iCal feed: it drops popup/email reminders (VALARMs).
[x] Repo: public GitHub repo (github.com/adamwitwer/nudge), MIT license. Secrets must never
    be committed (see section 4, Deployment).

4. ARCHITECTURE (as built)
--------------------------
Language/runtime: Python 3.11+ (the Pi has 3.11.2; the dev Mac has 3.14).
Dependencies: google-api-python-client, google-auth-oauthlib. Everything
else is stdlib (tomllib, sqlite3, urllib, zoneinfo). Dev: pytest.

Package layout (run as `python -m nudge <command>`):
  nudge/gcal.py         OAuth (calendar.readonly), token refresh, config-dir
                        lookup, calendarList / events.list (singleEvents)
                        and the account time zone (settings.get)
  nudge/triggers.py     pure: event -> Trigger(start, fire_at, minutes_before,
                        key). Handles popup-only, useDefault, all-day
                        wall-clock math, DST, declined and cancelled events.
  nudge/store.py        SQLite `handled(key, status sent|skipped, at)`,
                        pruned after 60 days.
                        key = calendar_id:event_id:start:minutes|notifier
                        A moved event gets a new key and fires again. The
                        per-notifier suffix means a failed destination is
                        retried alone.
  nudge/format.py       structured Message(title, detail, late, emoji) plus
                        renderers: as_markdown (Discord), as_html (Telegram)
  nudge/notifiers/      Notifier protocol; discord.py (webhook, mentions
                        disabled, 429 retry); telegram.py (Bot API
                        sendMessage, parse_mode=HTML, 429 retry; errors
                        never include the token-bearing URL)
  nudge/config.py       config.toml loader and validation
  nudge/engine.py       service loop
  nudge/__main__.py     CLI: auth | calendars | upcoming | test |
                        telegram-chats | run
  tests/                pytest: triggers, format, engine, config
  systemd/nudge.service

Service loop:
  every poll_minutes (5):   fetch events in [now - grace, now + 29 days]
                            for the configured calendars and rebuild the
                            triggers. On error, keep the last good list.
  every 30 s:               for each trigger with fire_at <= now that is not
                            yet handled:
                              late by at most grace (15 min): send; mark sent
                                (tagged "(late)" if more than 2 min late)
                              later than that: mark skipped and log
                              send failed: leave that notifier unmarked and
                                retry it alone next tick
  Google auth failure:      one Discord alert telling you to re-run
                            `nudge auth`, then retry every poll.
  Time zone:                taken from the Google account setting, not from
                            each calendar (the Family calendar is set to UTC).

Config and secrets (config.toml, with the Discord webhook and Telegram bot
token + chat_id; credentials.json, token.json, state.db),
in lookup order:
  1. $NUDGE_CONFIG_DIR
  2. the project folder, if it contains config.toml (the Pi: ~/Projects/nudge)
  3. ~/.config/nudge (the dev Mac)
All are gitignored and chmod 600. Only config.example.toml is committed.

Deployment (Pi 5, Debian 12, `raspberrypi`, LAN 192.168.50.167 / Tailscale
100.107.81.122): git clone in ~/Projects/nudge, venv/, the systemd unit
copied to /etc/systemd/system (Restart=always, User=adam), logs in journald
(`journalctl -u nudge`). Update with: git pull, pip install -e .,
systemctl restart nudge. Only the Pi runs `nudge run`.

5. MESSAGE FORMAT (MVP: title only)
-----------------------------------
  ⏰ **Dentist appointment** · in 10 minutes
  ⏰ **Dentist appointment** · in 1 hour 30 minutes
  ⏰ **Dentist appointment** · tomorrow at 9:00 AM      (leads of 6 h or more)
  ⏰ **Mom's birthday** · tomorrow                      (all-day)
  ⏰ **Dentist appointment** · in 5 minutes _(late)_

  - The wording is computed at send time from the event start.
  - Ideas for later: emoji keyword rules (🦷 dentist, 🎂 birthday, 💊 meds),
    start time, location.

7. RISKS
--------
- Refresh token revoked or expired -> handled: Discord alert, re-run
  `nudge auth`. The consent screen is In production, so there's no 7-day
  expiry.
- Pi SD card corruption -> state.db is disposable. Keep a copy of
  config.toml, credentials.json, and token.json off the Pi (the Mac has
  them in ~/.config/nudge).
- Home network outage -> late or skipped reminders. The grace window limits
  the damage. Acceptable for a personal tool.
- Two machines running `nudge run` -> duplicate messages. Only the Pi runs it.
